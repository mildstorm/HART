# 13. 메인 6502 ↔ U64 연결 방식 (분석 1차, 2026-11-23)

STM32 에뮬레이터에서 HART를 실기와 똑같이 돌리려면, 메인 CPU(U30)와 보조 CPU(U64)가 어떻게 주고받는지 알아야 합니다. 이 문서는 U65(U64 펌웨어)와 U45(메인 $C300·$C800 펌웨어) 덤프를 **실제로 실행되는 코드만 따라가며**(리셋·진입점부터 분기를 추적하는 역어셈블) 읽은 결과입니다.

표기: **확인** = 코드에서 직접 보임, **추정** = 코드 정황에서 유추, 회로로 아직 확인 안 함.

---

## 1. U65는 $C000(과 $E000)에 놓인다 — 기존 역어셈블리 주소 정정

| 벡터 | 값 | 뜻 |
| :--- | :--- | :--- |
| RESET | `$C000` | 롬 첫 바이트(`D8` CLD)에서 시작 (**확인**) |
| IRQ | `$2120` | 롬 밖 |
| NMI | `$0016` | 롬 밖 |

* 리셋 벡터가 `$C000`이므로 U65는 U64 버스의 **$C000–$DFFF**에 있고, 벡터를 $FFFA에서 읽으려면 **$E000–$FFFF에도 같은 롬이 비쳐야** 합니다(A13 미디코드, **추정**이지만 다른 배치로는 부팅 불가).
* [`disasm/U65_VD5.asm`](../disasm/U65_VD5.asm)은 시작 주소를 `$E000`으로 잡았습니다. 롬 안의 점프·테이블 주소(`JMP $D16E`, `LDA $C991,X` 등)는 `$C000` 기준이므로, 그 파일의 주소는 `-$2000` 해서 읽어야 합니다.

## 2. U64 로컬 버스 주소 맵 (U65 코드 기준)

| U64 주소 | 쓰임 (코드) | 판단 |
| :--- | :--- | :--- |
| `$4000–$43FF` | 리셋 시 0으로 지움, `$43C0,X` 읽기, `$43E8–$43FF` 변수 | **U68 6116의 짝수 바이트** (아래 3절) |
| `$5000–$53FF` | 리셋 시 0으로 지움, `$53C0,X` 읽기, `$53F6–$53FF` 변수 | **U68 6116의 홀수 바이트** |
| `$8000–$800C` | 13개 주소를 차례로 읽고 각각 `CMP #$FF` (눌린 키가 0) | **키보드 매트릭스 13행 스캔** (**확인**: 스캔 루프 `$CA1C–$CA99`) |
| `$8800` | 하위 4비트를 읽어 표(`$C991`, `$C9A1`)로 변환 | 스위치/모드 입력 (**추정**: DIP·한영 등) |
| `$0400` (쓰기) | 보낼 문자를 쓰고 `$43EE`에 사본 저장. 기능키 줄(`$43C0,X`) 글자를 하나씩 여기로 보냄 | **메인 CPU로 가는 키 코드 래치** (**추정**, 메인 `$C000`에서 읽힘) |
| `$0800` (쓰기) | 초기화 때 `$82` | 제어 래치 (**미상**) |
| `$0C00` (쓰기) | `$8800` 값을 표로 바꿔 씀 | 비디오/모드 래치 (**추정**: U69 74LS273) |
| `$0000–$03FF` | `STX $02 / STY $0002 / STX $03`가 반복해서 나옴 | 일반 RAM이 아님 (**추정**). U64는 따로 작업 RAM이 없고 변수를 U68 꼭대기에 둔다 |
| `$C000–$DFFF` (+`$E000–$FFFF`) | 펌웨어 | U65 |

* 결론: **U64가 키보드를 직접 스캔하는 키보드 컨트롤러**이기도 합니다. Disp 키가 메인 CPU와 상관없이 기능키 줄을 바꾸던 현상([08](08-repair-log.md), [09](09-verified-baseline.md))과 맞습니다.
* 기능키는 **매크로**로 보입니다: F 키를 누르면 U64가 기능키 줄(행 24)의 라벨 글자를 `$0400`으로 한 글자씩 보내, 메인 CPU에는 그 글자를 친 것처럼 들어갑니다 (**추정**).

## 3. U68은 두 CPU가 함께 쓰는 80컬럼 화면 메모리

메인 쪽 80컬럼 펌웨어(U45 `$C300–$C3FF`, `$C800–$CFFF`)는 Videx 카드 하드웨어(`$C0B0` CRTC, `$CC00` 화면 RAM)를 **전혀 쓰지 않습니다**. 대신 **`$E000–$E7FF`**를 씁니다 (**확인**: `LDA $E780,Y`, `STA $E7D2,Y`, `ORA $E7EC` 등).

| 메인 CPU 주소 | 내용 |
| :--- | :--- |
| `$E000–$E77F` | 80컬럼 × 24행 화면 (한 행 80바이트, 선형) |
| `$E780–$E7CF` | 행 24 = **기능키 줄** (80글자. `$C315–$C398`이 이 줄을 편집, `CPY #$4F`) |
| `$E7D0–$E7FF` | 80컬럼 펌웨어 변수 (`$E7D2,Y` = 기능키 12개 위치표, `$E7EA` = 기능키 번호, `$E7EC` = 상태) |

> **측정으로 재검토 중 (2026-11-23)**: U68 A0(핀 8)은 U58(74LS157) 1Y에서 오고, 그 입력 1A(핀 2)는 **U64 A7(핀 16)**입니다 ([netlist](../data/netlist.csv)). 아래의 "U64 A12 = 짝/홀 선택" 대응은 U64 주소선이 U68에 순서대로 붙는다는 가정이었는데, 실제로는 순서가 섞여 있습니다. 변수 위치가 맞아떨어진 것은 사실이지만, 정확한 대응은 U68 A0–A10 각각의 MUX 입력을 다 재야 확정됩니다.

### U68 주소 핀 배선 (측정, 2026-11-24)

U68 A0–A10은 모두 74LS157(U47·U58·U59) 출력에서 옵니다. 세 칩은 /G가 GND라 항상 켜져 있고, SELECT(핀 1) 셋은 한 넷이며 U60-13에도 붙습니다(출처 미확인, U64·U30 핀과 직결 아님). B 입력은 모두 메인 주소 버퍼(U31·U32·U33 74LS367)를 거쳐 메인 CPU 주소선에 붙습니다.

| U68 | MUX | A 입력 (U64 쪽) | B 입력 경로 | 메인 주소 |
| :--- | :--- | :--- | :--- | :--- |
| A0 | U58 1Y | U64 A7 | U31 9←10 | **A8** |
| A1 | U59 4Y | U64 A9 | U32 11←12 | **A10** |
| A2 | U59 3Y | U64 A4 | U32 13←14 | **A5** |
| A3 | U59 2Y | U64 A5 | U31 5←4 | **A6** |
| A4 | U59 1Y | U64 A8 | U31 7←6 | **A9** |
| A5 | U58 2Y | U64 A6 | U32 9←10 | **A7** |
| A6 | U47 1Y | U64 A2 | U31 3←2 | **A3** |
| A7 | U47 2Y | U64 A1 | U32 3←2 | **A2** |
| A8 | U47 3Y | ? (U47-11. U64 A12와는 불통) | U33 3←2 | **A0** |
| A9 | U47 4Y | U64 A0 | U33 13←14 | **A1** |
| A10 | U58 4Y | U64 A3 | U31 13←14 | **A4** |

* 양쪽 모두 순서 없이 섞여 붙지만, 측정한 10개 핀 모두에서 **U64 A(k−1) ↔ 메인 Ak** 관계가 성립합니다. 따라서 섞임은 서로 상쇄되고, 두 CPU 사이 대응은 비트 섞임과 무관하게 정해집니다.
* 남은 U68 A8은 메인 A0과 짝이므로 U64 쪽은 A0–A9 밖의 선, 곧 **U64 A12**일 것으로 봤으나 U47-11 ↔ U64-22는 **불통**(2026-11-24). U47을 소켓에서 뽑고 소켓 11번 자리를 재 보니 GND 33.3MΩ, +5V 21.35MΩ로 **어디에도 연결되지 않음**. 뒷면 사진에도 이 패드에 선이 없음.
  * 이대로면 U64 접근 때 U68 A8이 늘 High(1)라 U64 `$4000+k`와 `$5000+k`가 같은 바이트가 됨.
  * 그런데 U65 코드는 두 영역을 서로 다른 변수로 씀: `$53E8–$53F4`를 0으로 지우면서 `$43E8–$43F4`는 플래그로 유지, `$43F7`은 인덱스인데 `JMP ($53F7)`은 포인터, `$43F6`·`$53F6` 따로 읽고 씀. 서로 겹치면 펌웨어가 정상 동작할 수 없음.
  * **정정 (같은 날)**: U47-11은 **U48(74LS02 NOR) 3Y(핀 10)**와 도통. 연결 없음이 아니라 NOR 게이트 출력에서 옴 (위 저항값은 꺼진 TTL 출력이라 높게 나온 것으로 봄). U48 3B(핀 9) = **U64 A12** (측정). 다른 입력 3A(핀 8)는 U34-4와 같은 넷이고 출처 미확인. 따라서 U64 접근 때 U68 A8 = NOR(A12, 48-8). 48-8이 Low이면 A8 = /A12 → **U64 `$4000+k` = 메인 `$E000 + 2k + 1`(홀수), `$5000+k` = 메인 `$E000 + 2k`(짝수)**로, 아래 표의 짝/홀과 반대가 됨. 48-8은 U34-4·U34-10과 같은 넷이고, **U33-4(74LS367 2번 버퍼 입력)**와 도통. U33-5 → U30 핀 37(Φ0)이므로 이 넷은 **버퍼 전 메인 Φ0 클럭**. 따라서 U68 A8(U64 쪽) = NOR(U64 A12, Φ0): Φ0가 Low인 반주기(메인 CPU가 버스를 안 쓰는 φ1 쪽)에 A8 = /A12. U64가 U68을 쓰는 것은 이 반주기로 보이며, 이때 `$4000` = 홀수 칸, `$5000` = 짝수 칸. SELECT 넷(U47·U58·U59 핀 1, U60-13)은 클럭이 아니라 **U51(82S129 디코드 PROM "2") 핀 11**에서 옴 (측정 2026-11-24). 표준 핀배치로 핀 11 = O2(bit1)이고, 덤프에서 bit1이 1인 입력은 256개 중 12개(`$2C/2D/3C/3D/6C/6D/7C/7D/AC/AD/EC/ED`)뿐. 74LS157은 SELECT=High일 때 B(메인)를 고르므로, **평소에는 U64가 U68을 쥐고, 특정 디코드 조건에서만 메인 CPU가 U68을 봄**(추정). 덤프에서 정리한 논리식(256개 전부 확인): **O2 = A5 · A3 · A2 · /A1 · /(A7 · A4)** (A0, A6 무관). 칩 핀으로는 핀 2·4·7 = High, 핀 6 = Low, 핀 15와 핀 3이 둘 다 High면 안 됨. 측정된 입력: 핀 1(A6) = U64 R/W(SELECT와 무관), **핀 7(A2) = Φ0** → SELECT는 Φ0 High(메인 CPU 버스 반주기)에만 1이 될 수 있음. 핀 2(A5) = U48 1Y(NOR, 입력 48-2·48-3 미확인), 핀 15(A7) = U48 2Y(NOR: 48-5, 48-6). 48-5 = U35 /1G = **U62 2번 FF /Q**. 이 FF는 D=GND, **/PRE = U22(74LS138) Y3**(I/O SELECT 디코더라면 `$C3xx`), **CLK = U35 1Y3**(꺼지는 주소, `$CFFF` 추정) → **Videx식 확장 롬 스위치**: 슬롯 3 롬(`$C3xx`)에 접근하면 켜지고, 꺼짐 주소에 접근하면 꺼짐 (추정). 켜져 있을 때 메인이 U68(및 `$C800` 롬)을 보는 것으로 보임. 남은 것: 핀 3·4·5·6, 48-2·3·6, U22 enable: /G2A = U76 /2Q(타이밍), /G2B = 메인 A11, G1 = **U50 O4(핀 9)**. U50 덤프에서 O4 = /A0 · /A6 (칩 핀 5, 핀 1이 둘 다 Low, A1(핀 6)은 GND 고정) → 측정: 핀 5 = 메인 A13(U33 버퍼), 핀 1 = U34 1Y = NAND(A15, A14)(U32 버퍼). 따라서 **U22 Y3(U62 켜기) = A15·A14 = 1, A13 = 0, A11 = 0, A10–A8 = 011, U76 /2Q 타이밍** → `$C300–$C3FF`. A12는 아직 어느 조건에도 안 보임(그대로면 `$D3xx`에서도 켜짐 — Applesoft가 `$D3xx`에서 실행되므로 실제로는 A12도 어딘가에서 걸러질 것, 22-4/U76 쪽 확인 필요). U22 입력 A·B·C = 메인 A8·A9·A10(버퍼 경유, 측정) → Y3 = `$x3xx`. U62 /CLR(13) = U30 SO = +5V(측정) → 리셋으로 지워지지 않음. **끄기**: U35 1번 디코더 입력 A = 메인 A10, B = 메인 A9(버퍼 경유, 측정), /1G = U62 /2Q → 스위치가 켜진 동안 A10·A9 = 11인 주소에 접근하면 그 접근이 끝날 때 꺼짐. `$CE00–$CFFF`(Videx의 `$CFFF` 끄기와 같은 자리)가 여기에 들지만, 상위 주소 조건이 없어 `$x600–$x7FF`, `$xE00–$xFFF`도 해당. 그러면 `$E780` 같은 접근 뒤에도 꺼지게 되므로, 실제 동작은 U45 코드 흐름과 맞춰 확인 필요 (추정, 미확정).
  * **U45 코드 대조 (2026-11-25)**: `$C300` 진입은 Videx와 같음(`BIT $FFCB` → `STA $CFFF` → `JSR $CAA7`). `$C315–$C3DF` 기능키 편집 루틴은 `$C3xx`에서 실행되면서 `$E7EC`, `$E780,Y`, `$E7D2,Y`, `$E7EA`를 계속 읽고 씀. 이 접근(A10·A9 = 11)마다 스위치가 꺼져도 다음 명령을 `$C3xx`에서 가져오는 순간 다시 켜지므로 **`$C3xx` 코드는 문제없이 동작**. `$C800–$CBFF` 코드의 절대 주소 접근은 `$E7xx` 변수 8곳뿐(`$E7E7`, `$E7FF`, `$E7EC`, `$E7DF`)이고 화면은 `($28),Y` 같은 간접 주소로 씀.
  * 다만 측정된 SELECT 논리에서 U62 /Q는 U48 2번 NOR(48-5)를 거쳐 U51 핀 15로 가므로, **스위치가 꺼져 있을 때(/Q=1) 핀 15 = 0이 되어 SELECT 조건 하나가 풀림**. 즉 "켜져 있을 때만 메인이 U68을 본다"는 단순한 해석과 극성이 맞지 않음. U51 핀 3·4·6과 U48 핀 2·3·6을 재야 판정 가능. U51 입력 핀(1–7, 15)이 어느 신호인지 알면 "메인이 언제 `$E000–$E7FF`에서 U68을 보는가"(3절 남은 의문)가 풀림. U65·U45 코드 대응은 이 기준으로 다시 맞춰야 함. 그러면 아래 "짝/홀" 대응이 그대로 맞습니다: 메인 `$E000+n` ↔ U64 `$4000 + (n>>1)`(n 짝수) / `$5000 + (n>>1)`(n 홀수).
* 에뮬레이터에서는 U68을 메인 주소 순서(`n`)로 2KB 배열 하나로 두고, U64 쪽 접근은 `n = (k<<1) | A12`로 바꾸면 됩니다. 비트 섞임은 양쪽이 같이 바뀌므로 무시해도 됩니다(화면 표시는 메인 순서 기준이 맞는지는 비디오 카운터 쪽 확인 필요).

두 CPU 쪽 주소를 아래처럼 대응시키면 양쪽 변수와 화면 위치가 모두 맞아떨어집니다 (**추정, 위 측정과 충돌하므로 재검토**):

```
메인 $E000 + n   ↔   U68 바이트 n
U64  $4000 + k   ↔   U68 바이트 2k     (짝수 = 짝수 칸)
U64  $5000 + k   ↔   U68 바이트 2k+1   (홀수 = 홀수 칸)
```

| 메인 쪽 | U68 | U64 쪽 | 양쪽 코드 |
| :--- | :--- | :--- | :--- |
| `$E780` 행 24 시작 | `$780` | `$43C0` / `$53C0` | 메인이 기능키 줄 작성 ↔ U64가 `$43C0,X`·`$53C0,X`로 읽음 |
| `$E7D0` | `$7D0` | `$43E8` | 메인 `INC $E7D0` ↔ U64 `STA/ORA $43E8` |
| `$E7D2,Y` | `$7D2+` | `$43E9+` | 메인 기능키 위치표 ↔ U64 `$43E9–$43F5` 사용 |
| `$E7EA` | `$7EA` | `$43F5` | 메인 기능키 번호 ↔ U64 `LDX $43F5` |
| `$E7EC` | `$7EC` | `$43F6` | 메인 상태 비트7 ↔ U64 `LDY/AND/STA $43F6` |

즉 U64 화면 처리에서 한 행은 짝수 칸 40바이트(`$4000+40×행`) + 홀수 칸 40바이트(`$5000+40×행`)이고, 행 24(`$3C0`)가 기능키 줄입니다. 80컬럼에서 한 번에 두 글자를 내보내는 비디오 회로 구조(U66 래치, U71 74LS166 시프트)와도 어울립니다.

### 남은 의문 (메인 쪽)

* 메인 `$E000–$E7FF`는 원래 U46(Applesoft 후반부) 롬 자리입니다. 80컬럼 펌웨어가 이 영역을 **읽기까지** 하므로(`LDA $E780,Y`), 어떤 조건에서 이 2KB가 롬 대신 U68로 바뀌는지가 핵심입니다. 후보: `$C800` 확장 롬이 켜져 있는 동안, 또는 `$C001–$C003` 스위치(U45 `$C360 BIT $C002`, `$C722 BIT $C001` 등).
* 이것은 디코드 PROM(U36·U38·U50·U51) 입력핀 배선을 알면 확정할 수 있습니다.

---

## 4. 에뮬레이터에 필요한 것 (다음 단계)

1. **U64 6502 하나 더**: U65를 `$C000`/`$E000`에, U68을 위 대응대로 `$4000`/`$5000`에, 키보드 행 `$8000–$800C`, 스위치 `$8800`, 래치 `$0400/$0800/$0C00`.
2. **메인 쪽**: U68을 `$E000–$E7FF`에 언제 보이게 할지(3절 의문), `$0400` 래치를 메인 `$C000` 키 입력으로 연결.
3. **화면**: U68 80×25를 U70 폰트로 그리기(행 24 = 기능키 줄). 한글 조합(뱅크 3)은 U65의 변환 루틴 해석 후.
4. **키보드**: PC 키 → HART 키 매트릭스(13행 × 8열) 표. 행·열 배치는 J10 배선([05](05-interface-pinouts.md))과 U65 스캔 루틴의 키 코드표에서 만들어야 함.

## 5. 확인하면 좋은 측정 (실기)

측정 위치 그림: [`analysis/u64_interface_measure.jpg`](../analysis/u64_interface_measure.jpg) (`tools/annotate_u64_interface.py`로 생성)

* U64 주소선 A10·A11·A12·A14·A15가 어느 칩(디코더)으로 가는지 → `$0400/$0800/$0C00`, `$4000/$5000`, `$8000/$8800` 디코드 확정
* U68 주소 핀 A0이 메인 쪽 A0과 U64 쪽 A12 중 무엇에 붙는지 (짝/홀 분할 확인)
* 메인 `$C000` 키 데이터가 U64 `$0400` 래치 출력에서 오는지 (래치 칩 확인)

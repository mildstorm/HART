# 13. 메인 6502 ↔ U64 연결 방식 (분석 1차, 2026-11-23)

STM32 에뮬레이터에서 HART를 실기와 똑같이 돌리려면, 메인 CPU(U30)와 보조 CPU(U64)가 어떻게 주고받는지 알아야 합니다. 이 문서는 U65(U64 펌웨어)와 U45(메인 $C300·$C800 펌웨어) 덤프를 **실제로 실행되는 코드만 따라가며**(리셋·진입점부터 분기를 추적하는 역어셈블) 읽은 결과입니다.

표기: **확인** = 코드에서 직접 보임, **추정** = 코드 정황에서 유추, 회로로 아직 확인 안 함.

---

## 1. U65는 $C000(과 $E000)에 놓인다 — 기존 역어셈블리 주소 정정

| 벡터 | 값 | 뜻 |
| :--- | :--- | :--- |
| RESET | `$C000` | 롬 첫 바이트(`D8` CLD)에서 시작 (**확인**) |
| IRQ | `$2120` | 롬 밖 |
| NMI | `$0016` | 롬 밖 |

* 리셋 벡터가 `$C000`이므로 U65는 U64 버스의 **$C000–$DFFF**에 있고, 벡터를 $FFFA에서 읽으려면 **$E000–$FFFF에도 같은 롬이 비쳐야** 합니다(A13 미디코드, **추정**이지만 다른 배치로는 부팅 불가).
* [`disasm/U65_VD5.asm`](../disasm/U65_VD5.asm)은 처음에 시작 주소를 `$E000`으로 잡았으나, 2026-11-26 `tools/disasm6502.py`로 `$C000` 기준·U64 주소 맵 주석으로 다시 만들었습니다(이제 주소를 그대로 읽으면 됨).

## 2. U64 로컬 버스 주소 맵 (U65 코드 기준)

| U64 주소 | 쓰임 (코드) | 판단 |
| :--- | :--- | :--- |
| `$4000–$43FF` | 리셋 시 0으로 지움, `$43C0,X` 읽기, `$43E8–$43FF` 변수 | **U68 6116의 홀수 칸** (메인 `$E000+2k+1`, 3.1절 측정) |
| `$5000–$53FF` | 리셋 시 0으로 지움, `$53C0,X` 읽기, `$53F6–$53FF` 변수 | **U68 6116의 짝수 칸** (메인 `$E000+2k`) |
| `$8000–$800C` | 13개 주소를 차례로 읽고 각각 `CMP #$FF` (눌린 키가 0) | **키보드 매트릭스 13행 스캔** (**확인**: 스캔 루프 `$CA1C–$CA99`) |
| `$8800` | 하위 4비트를 읽어 표(`$C991`, `$C9A1`)로 변환 | 스위치/모드 입력 (**추정**: DIP·한영 등) |
| `$0400` (쓰기) | 보낼 문자를 쓰고 `$43EE`에 사본 저장. 기능키 줄(`$43C0,X`) 글자를 하나씩 여기로 보냄 | **메인 CPU로 가는 키 코드 래치** (**추정**, 메인 `$C000`에서 읽힘) |
| `$0800` (쓰기) | 초기화 때 `$82` | 제어 래치 (**미상**) |
| `$0C00` (쓰기) | `$8800` 값을 표로 바꿔 씀 | 비디오/모드 래치 (**추정**: U69 74LS273) |
| `$0000–$03FF` | `STX $02 / STY $0002 / STX $03`가 반복해서 나옴 | 일반 RAM이 아님 (**추정**). U64는 따로 작업 RAM이 없고 변수를 U68 꼭대기에 둔다 |
| `$C000–$DFFF` (+`$E000–$FFFF`) | 펌웨어 | U65 |

* 결론: **U64가 키보드를 직접 스캔하는 키보드 컨트롤러**이기도 합니다. Disp 키가 메인 CPU와 상관없이 기능키 줄을 바꾸던 현상([08](08-repair-log.md), [09](09-verified-baseline.md))과 맞습니다.
* 기능키는 **매크로**로 보입니다: F 키를 누르면 U64가 기능키 줄(행 24)의 라벨 글자를 `$0400`으로 한 글자씩 보내, 메인 CPU에는 그 글자를 친 것처럼 들어갑니다 (**추정**).

## 3. U68은 두 CPU가 함께 쓰는 80컬럼 화면 메모리

메인 쪽 80컬럼 펌웨어(U45 `$C300–$C3FF`, `$C800–$CFFF`)는 Videx 카드 하드웨어(`$C0B0` CRTC, `$CC00` 화면 RAM)를 **전혀 쓰지 않습니다**. 대신 **`$E000–$E7FF`**를 씁니다 (**확인**: `LDA $E780,Y`, `STA $E7D2,Y`, `ORA $E7EC` 등).

| 메인 CPU 주소 | 내용 |
| :--- | :--- |
| `$E000–$E77F` | 80컬럼 × 24행 화면 (한 행 80바이트, 선형) |
| `$E780–$E7CF` | 행 24 = **기능키 줄** (80글자. `$C315–$C398`이 이 줄을 편집, `CPY #$4F`) |
| `$E7D0–$E7FF` | 80컬럼 펌웨어 변수 (`$E7D2,Y` = 기능키 12개 위치표, `$E7EA` = 기능키 번호, `$E7EC` = 상태) |

### 3.1 U68 주소 핀 배선 (측정, 2026-11-24)

U68 A0–A10은 모두 74LS157(U47·U58·U59) 출력에서 옵니다. 세 칩은 /G가 GND라 항상 켜져 있습니다. SELECT(핀 1) 셋은 한 넷이고, SELECT가 Low이면 A 입력(U64 쪽), High이면 B 입력(메인 쪽)을 고릅니다. B 입력은 모두 메인 주소 버퍼(U31·U32·U33, 74LS367)를 거쳐 메인 CPU 주소선에 붙습니다.

| U68 | MUX | A 입력 (U64 쪽) | B 입력 경로 | 메인 주소 |
| :--- | :--- | :--- | :--- | :--- |
| A0 | U58 1Y | U64 A7 | U31 9←10 | A8 |
| A1 | U59 4Y | U64 A9 | U32 11←12 | A10 |
| A2 | U59 3Y | U64 A4 | U32 13←14 | A5 |
| A3 | U59 2Y | U64 A5 | U31 5←4 | A6 |
| A4 | U59 1Y | U64 A8 | U31 7←6 | A9 |
| A5 | U58 2Y | U64 A6 | U32 9←10 | A7 |
| A6 | U47 1Y | U64 A2 | U31 3←2 | A3 |
| A7 | U47 2Y | U64 A1 | U32 3←2 | A2 |
| A8 | U47 3Y | **NOR(U64 A12, Φ0)** (U48 3Y) | U33 3←2 | A0 |
| A9 | U47 4Y | U64 A0 | U33 13←14 | A1 |
| A10 | U58 4Y | U64 A3 | U31 13←14 | A4 |

* 양쪽 모두 순서가 섞여 붙지만, A8을 뺀 10개 핀 모두에서 **U64 A(k−1) ↔ 메인 Ak**가 성립합니다. 섞임이 서로 상쇄되므로 두 CPU 사이 대응은 비트 순서와 상관없이 정해집니다.
* U68 A8(U64 쪽)은 U48(74LS02) 3Y = NOR(U64 A12, Φ0)입니다. Φ0는 U33-4(버퍼 전 메인 Φ0)입니다. Φ0가 Low인 반주기에 A8 = /A12입니다. (처음에 U47-11이 어디에도 안 붙은 것처럼 측정됐으나, 나중에 U48-10과 도통으로 정정.)
* 따라서 U64가 U68을 쓰는 반주기에는 다음과 같습니다.

```
메인 $E000 + n   ↔   U68 바이트 n (메인 주소 순서로 본 위치)
U64  $4000 + k   ↔   메인 $E000 + 2k + 1   (홀수 칸, A12=0 → A8=1)
U64  $5000 + k   ↔   메인 $E000 + 2k       (짝수 칸, A12=1 → A8=0)
```

* 처음 롬 코드만 보고 세운 대응(`$4000` = 짝수, `$5000` = 홀수)과 **반대**입니다. 아래 3.3의 변수 대응표는 그 옛 추정이라 다시 맞춰야 합니다.
* 에뮬레이터: U68을 메인 주소 순서(`n`)로 2KB 배열 하나로 두고, U64 쪽 접근은 `n = (k << 1) | (A12 ? 0 : 1)`로 바꿉니다. 화면 표시 순서가 메인 순서와 같은지는 비디오 카운터 쪽 확인이 필요합니다.

### 3.2 메인 CPU가 U68을 보는 조건 (측정 진행 중)

**SELECT = U51(82S129, 라벨 "2") O2(핀 11)**. 덤프에서 정리한 논리식(256개 전부 확인)은 다음과 같습니다.

> O2 = A5 · A3 · A2 · /A1 · /(A7 · A4)  (A0, A6 무관)
> 칩 핀으로: 핀 2·4·7 = High, 핀 6 = Low, 핀 15와 핀 3이 동시에 High가 아님

| U51 핀 (주소 비트) | 연결 (측정) | SELECT 조건 |
| :--- | :--- | :--- |
| 1 (A6) | U64 R/W | 무관 |
| 2 (A5) | U48 1Y = NOR(48-2, 48-3) | High |
| 3 (A4) | ? | 핀 15와 동시 High 금지 |
| 4 (A3) | U77 1Y2 | High |
| 5 (A0) | ? | 무관 |
| 6 (A1) | U35 2Y2 (/2G = U34 2Y = NAND(Φ0, 34-5), 2B = U36 O1, 2A = U36 O2) | Low → **2Y2 = Φ0 · U51 O4 · `$E000–$EFFF`** (롬 창 enable = U36 O4) (U36 보정 덤프, 2026-11-26, 3.2.1절) |
| 7 (A2) | Φ0 (U33-4) | High → 메인 Φ0 반주기에만 |
| 15 (A7) | U48 2Y = NOR(U62 /2Q, 48-6) | 핀 3과 동시 High 금지 |

**U62 2번 플립플롭 (Videx식 스위치)**: D = GND, /CLR = +5V(U30 SO), /Q → U35 /1G, U48-5.

| 동작 | 신호 | 조건 |
| :--- | :--- | :--- |
| 켜기 (/PRE) | U22(74LS138) Y3 | A15·A14 = 11 (U34 NAND → U50 핀 1), A13 = 0 (U50 핀 5), A11 = 0 (U22 /G2B), A10–A8 = 011 (U22 A·B·C), U76 /2Q 타이밍 (U22 /G2A) → **`$C300–$C3FF`** |
| 끄기 (CLK) | U35 1Y3 | 스위치가 켜진 동안 A10·A9 = 11 접근이 끝날 때 (`$CE00–$CFFF` 포함, 상위 주소 조건 없음) |

* U22 G1 = U50 O4. U50 덤프에서 O4 = /핀5 · /핀1 · /핀6. 핀 6은 처음 GND로 기록했으나 단락 중 측정이었고, 실제로는 **버퍼 A12**로 보임 (2026-11-27, U50 칩 내부에서 핀 6이 GND와 단락된 불량).
* A12 조건은 U50 핀 6에 있습니다(A12 = 1이면 O4 = 0). 정상 칩이면 `$C3xx`에서만 켜지고, 지금 불량 U50(핀 6이 GND에 붙음)으로는 `$D3xx`에서도 켜질 수 있습니다(추정).
* U76 2번 FF는 J = U74 1Y, /K = 그 반전(U72), /PRE·/CLR = +5V → T 플립플롭(분주기). U22를 정해진 클럭 구간에만 켜는 타이밍 신호로 봅니다.
* **U45 코드 대조 (2026-11-25)**: `$C300` 진입은 Videx와 같습니다(`BIT $FFCB` → `STA $CFFF` → `JSR $CAA7`). `$C315–$C3DF` 기능키 편집 루틴은 `$C3xx`에서 실행되면서 `$E7xx` 변수를 계속 읽고 씁니다. 그때마다 스위치가 꺼져도 다음 명령을 `$C3xx`에서 가져오면 다시 켜지므로 동작에는 문제없습니다. `$C800–$CBFF` 코드의 절대 주소 접근은 `$E7xx` 변수 8곳뿐이고, 화면은 `($28),Y` 같은 간접 주소로 씁니다.
* **극성 문제 (미해결)**: U62 /Q는 U48 NOR를 거쳐 U51 핀 15로 갑니다. 그래서 스위치가 **꺼져 있을 때**(/Q = 1) 핀 15 = 0이 되어 SELECT 조건 하나가 풀립니다. "켜져 있을 때만 메인이 U68을 본다"는 해석과 반대입니다. U51 핀 3, U48 핀 2·3·6, U35 2번 디코더·U77 1번 디코더 입력을 재야 판정됩니다 → [14](14-measure-todo.md) A절.

### 3.2.1 롬 배치와 U36 덤프 주소선 보정 (2026-11-26, 보정 적용 — U36 재덤프로 확인 예정)

> `rom/U36_3.bin`은 이 절의 보정을 적용한 파일입니다. 처음 읽은 파일(`f9397eb7…`)은 git 기록에만 남김. 보정본을 표준 순서로 풀면 (`$C000–$FFFF`, Φ0 기준, U35 enable = U36 O4): **U46 /CE = U51 O4·X·`$F000` + /3Q·/U51 O4·X·`$E000–$FFFF`**, **2Y2(→ U51-6, U68) = U51 O4·`$E000–$EFFF`**, **롬 A12 ≈ 메인 A12**.

**측정으로 확정된 것**: U45 /CE = U35 2Y0, U46 /CE = U35 2Y1, U45·U46 A12(핀 2) = U36 O3(핀 10), U35 2B·2A = U36 O1·O2, U35 /2G = NAND(Φ0, U36 O4) (34-5 ↔ 36-9, 11-26 정정: 처음엔 U49 2Q로 기록). U36 입력: 핀 1 = U51 O4, 2 = NAND(A15, A14), 4 = A12, 5 = U49 2Q, 6 = A13, 7 = GND, 15 = U49 3Q, 3 = 미확인(X), /CE1·/CE2 = GND. 동작 중 롬 A12(46-2) 0.14V.

**롬 코드로 정한 4KB 블록 위치** (JSR/JMP 절대 주소 분포): U45 앞쪽 4KB = `$C000`, U45 뒤쪽 = `$D000`, U46 앞쪽 = `$E000`, U46 뒤쪽 = `$F000` (Apple II+ 그대로, 리셋 벡터 `FA62`는 U46 뒤쪽).

**모순**: `rom/U36_3.bin`을 README 결선(덤프 비트 2·3·4 = 칩 핀 7·4·3)대로 풀면 O3는 핀 7 = 1일 때만 1이라 롬 A12가 늘 0이고, U46은 `$F000` 창에서만 선택되어 위 배치를 만들 수 없음. 입력 이름을 두 개 바꾸거나 출력 비트 순서를 바꿔도 안 됨 (전수 대입).

**해결 (정정 2026-11-26)**: U36 핀 4는 A12가 아니라 **버퍼 R/W**(U33 핀 11), 핀 3이 **A12**로 보임(버퍼 18칸 배분). 이 이름으로 6가지 순열을 대입하면 **덤프 비트 2와 4(칩 핀 7과 3)가 바뀐 경우 하나만** 맞음 → 덤퍼 ZIF 7·3번 점퍼가 서로 바뀐 것. 결과는 Apple 랭귀지 카드 그대로: 읽기 3Q = 0 → `$D000` U45 뒤·`$E000` U46 앞·`$F000` U46 뒤, 읽기 3Q = 1 → 롬 꺼짐(RAM), 쓰기 2Q = 1 → 롬 꺼짐(RAM 쓰기), 2Q = 0 → 2Y3(쓰기 막음). U50 덤프는 그대로 1Q = 쓰기 준비, 2Q = 쓰기 허용, 3Q = A0 XNOR A1. 아래 옛 표는 이름이 다를 뿐 같은 결과. 이때 표 (U49 Q는 동작 중 모두 0으로 측정됨, X = 1, 아래 표의 2Q 조건은 옛 해석):

| U51 O4 | U49 3Q | `$C000` | `$D000` | `$E000` | `$F000` |
| :--- | :--- | :--- | :--- | :--- | :--- |
| 0 | 0 | 2Y3 (35-9) | U45 뒤 | U46 앞 | U46 뒤 → **Apple II+ 롬** |
| 0 | 1 | 2Y3 | U45 뒤 | U45 앞 | U45 뒤 |
| 1 | x | U45 앞 | U45 앞 | **2Y2 → U51 → U68** | U46 뒤 |

* U51 O4 = 1이면 `$E000` 창이 U68(80컬럼 공유 화면)으로 가고, 2Y2 → U51 A1 되먹임이 O4를 유지 → 80컬럼 모드 래치로 해석됨.
* X(핀 3) = 0이면 대부분 2Y3 → X는 R/W일 가능성.
* ~~사각 격자 = U49 상태~~ **기각 (11-26)**: 정상·격자 상태 모두 U49 Q = 0으로 같음. 롬 창 enable은 U49가 아니라 U36 O4.
* 같은 날 같은 결선 세션에서 읽은 U38·U18·U17도 같은 순서 문제가 있을 수 있음. U50·U51(오후 2시대, 별도 세션)은 표준 순서로 풀어야 식이 맞음.

### 3.3 옛 변수 대응 (롬 코드 기준 추정, 3.1 측정과 짝/홀이 반대라 재검토 필요)

| 메인 쪽 | U64 쪽 (옛 추정) | 양쪽 코드 |
| :--- | :--- | :--- |
| `$E780` 행 24 시작 | `$43C0` / `$53C0` | 메인이 기능키 줄 작성 ↔ U64가 `$43C0,X`·`$53C0,X`로 읽음 |
| `$E7D0` | `$43E8` | 메인 `INC $E7D0` ↔ U64 `STA/ORA $43E8` |
| `$E7D2,Y` | `$43E9+` | 메인 기능키 위치표 ↔ U64 `$43E9–$43F5` 사용 |
| `$E7EA` | `$43F5` | 메인 기능키 번호 ↔ U64 `LDX $43F5` |
| `$E7EC` | `$43F6` | 메인 상태 비트7 ↔ U64 `LDY/AND/STA $43F6` |

3.1 측정대로라면 `$E7D0`(짝수)은 U64 `$53E8`, `$E7EC`는 `$53F6`에 대응합니다. U65 코드에서 `$53E8,X`·`$53E9,X`로 기능키 위치표의 차이를 구하는 부분(`$E83F–$E864`)과 맞는지 다시 대조해야 합니다.

### 남은 의문 (메인 쪽)

* 메인 `$E000–$E7FF`는 원래 U46(Applesoft 후반부) 롬 자리입니다. 어떤 조건에서 이 2KB가 롬 대신 U68로 바뀌는지는 3.2의 SELECT 조건과 U46 /CE·/OE를 확인해야 확정됩니다.

## 3.4 U65·U45를 실제로 돌려 알게 된 것 (2026-11-27, STM32 에뮬레이터 작업)

U65를 PC에서 6502로 실행하고(3.1의 U68 대응 그대로), 메인 쪽은 코어 II+에 HART 롬을 얹어 돌려 확인했습니다. 코드: STM32 저장소 `hart-core/` (`tests/run.ps1`로 재현).

**U64 (확인: 펌웨어 실행 결과)**

* **HART 로고는 U64가 직접 그립니다.** 리셋 후 약 3백만 사이클 안에 U68 행 8–13에 "ZW" 글자로 된 HART 큰 글씨, 행 16에 `Zung Won Co.,Ltd. 542-3675 SEOUL KOREA`. 메인 CPU와 무관 → 메인이 멈춰도 로고가 나오던 현상과 맞음.
* **U64 펌웨어는 소프트웨어 비디오 타이밍 엔진**입니다. 주사선 하나가 64사이클이고, 그 안을 `CMP #$00`·`NOP`로 채우며 `$0000`·`$0002`·`$0003`에 계속 씁니다(타이밍 래치). 스택 포인터(`TSX`/`TXS`)를 줄 카운터로 씁니다(RAM이 없음). 한 프레임은 16256사이클(254줄)이고, 그중 약 1.5줄 동안 `$0C00`이 `$E0`(그 밖에는 `$40`) → 수직 동기로 추정. 실행하는 명령의 절반이 `CMP #imm`입니다.
* `$0C00` 값은 `$8800` 스위치에 따라 바뀜: `$F0`/`$00` → `$00`, `$F2` → `$30`, `$F4`/`$FF` → `$40`, `$F8` → `$40`·`$80`.
* **Disp 키 = 행 7 비트 3**: 누르면 U68 행 24(메인 `$E780`)에 기능키 줄 `1GOSUB 2GOTO 3ONERR GOTO 4THEN 5NEXT 6DELETE 7CHR$(8MID$ 9RIGHT$`, `$01`·`$02`·`$03`(10·11·12번), `LEFT$ HOME STEP`이 써짐. 번호는 비트 7이 0(역상)으로 저장.
* **키 매트릭스** (행 `$8000+r`, 비트 0 = 눌림, 보낸 코드):

**메인 쪽 HART 창 (U45 코드로 확인, 기판 측정은 아직)**

* `$C000–$C003` 접근이 **주소선 A1로 창을 켜고 끔**: `$C002`·`$C003` = 켬, `$C000`·`$C001` = 끔. 80컬럼 펌웨어는 들어갈 때 `BIT $C002`, 나올 때 `LDA $C000`·`BIT $C001`. 키 입력은 `$C002` bit 7로 기다림(`$C86B`), 스트로브는 `$C010`·`$C011`·`$C012`로 지움(II+는 `$C010–$C01F` 모두 스트로브).
* 창이 켜지면 **`$D000–$DFFF` = U45 앞 4KB**, `$E000–$EFFF` = U68. 즉 `disasm/U45_CD8.asm`에서 `$C000–$CFFF`로 적힌 앞 4KB 중 `$C000–$C0FF`·`$C100–$C2FF`·`$C400–$C5FF` 등의 루틴은 실제로는 **`$D000`대에서 실행**됩니다(80컬럼 엔진, `JSR $D000`·`JSR $DC00` 등). `$C300`·`$C700`·`$C800–$CFFF`는 슬롯·확장 롬 자리에서 그대로 실행.
* Applesoft가 `$DB64`에서 `JSR COUT` → 80컬럼 펌웨어 → 창을 끄고 돌아와야 `$DB67`(Applesoft)로 정상 복귀. 창을 `$C001`로만 끄게 하면 여기서 U45 앞 4KB로 돌아가 BRK가 남 → `$C000`도 끄는 쪽이라는 근거.
* 행 2 비트 5·7: 누르고 있는 동안 키가 안 나감(용도 미확인, Vdx 키 후보).

**U68 화면을 U70으로 그리는 법 (에뮬레이터에서 맞춘 것, 2026-11-28)**

* U70 **뱅크 1**(`$0800–`)을 칸 값 그대로 글자 번호로 씀. 비트 7이 맨 왼쪽 점, 비트 0은 늘 1(7점), **켜진 비트 = 어두운 점**. 그래서 U64가 지우는 값 `$00` = 빈칸, `$80–$FF` 보통, `$20–$7F` 반전. 처음에 `$00`을 반전 `@`로 그렸더니 행 24와 로고 바탕이 블록으로 가득 찼음 → 이 극성이 맞음. 한글 모드에서 행 24에는 U64가 쓴 반전 `KOR`만 오른쪽에 남음.
* 뱅크 0은 `$40–$7F`만 보통 모양으로 다름 → FLASH용 짝 뱅크로 추정([12](12-memory-map.md) 4.3, [14](14-measure-todo.md) E7a). 에뮬레이터는 깜박임 없음.

## 3.5 한글 40×24 (2026-11-28, 롬을 실제로 돌려 확인)

광고의 "한글 40×24 표시 롬 내장"은 이렇게 동작합니다 (STM32 `hart-core/tests/hangul_run.cpp`로 재현, PR#7 → 한/영 → `gksrmf` → **한글** 확인).

* **PR#7 = 내장 한글 드라이버.** U45 `$C700` 페이지가 진입점(`SEC`/`CLC` → `BIT $C002`로 창 켜기). 초기화(`$D1A7`)가 CSW/KSW를 `$C703`/`$C726`으로 걸고, `$C054`·`$C057`·`$C052`·`$C050`(1페이지·고해상도·전체·그래픽)으로 바꾼 뒤 U68 `$E778`에 `$60`을 쓰고 `$9A`가 될 때까지 기다림.
* **U64가 글꼴과 그리기 루틴을 넘김.** U64가 이 요청을 보면 `$D500` 루틴이 작은 복사 프로그램을 U68(`$5000`, 짝수 칸)에 써서 실행하고, 그 프로그램이 U65 `$D780–$DF7F`(오프셋 `$1780–$1F7F`) 2KB를 U68 전체에 차례로 복사. 그래서 메인에서 `$E000+n` = U65 `$1780+n`: `$E000–$E07F`는 **메인이 실행하는 그리기 루틴**(스택에서 16바이트를 꺼내 `$5C00,X`…`$4000,X`, `$3C00,X`…`$2000,X`에 저장), `$E100–`은 글꼴(코드×8), 뒤쪽은 표(`$E0C0` 키→자모 분류, `$E75E` 글꼴 페이지). `$E778`은 그 복사로 `$9A`가 되어 기다림이 끝남.
* **한 글자 칸 = 16줄, 고해상도 두 페이지에 8줄씩.** 화면은 두 페이지를 한 줄씩 엇갈려 384줄(2페이지가 짝수 줄로 놓아야 글자가 바름 — 비디오 회로로는 미확인). 영문은 글꼴 줄을 두 번씩 써서 16줄.
* **창은 `$C100–$CFFF`도 덮음.** 엔진이 `JSR $C18E`로 `$C1` 페이지를 직접 부르므로, 창이 켜진 동안 `$C100–$DFFF` 전체가 U45 앞 4KB(디코드 표의 "U51 O4 = 1 → `$C000` U45 앞"과 일치).
* **입력:** 한/영 키(행 2·비트 6)를 누르면 U64가 글자 키를 비트 7 없이 보냄(`g` → `$47`). 메인은 키를 `$C000`이 아니라 U68 `$E7DD`(U64 `$43EE` 사본)에서 읽으므로(`JSR $D000` → `LDA $E7DD`) 비트 7 정보가 남음. Caps Lock이 켜져 있으면 대문자 = Shift라 쌍자음(ㄲ·ㄸ…)이 됨. 출력 쪽 한글 구간은 Ctrl+N(`$8E`)~Ctrl+O(`$8F`), 상태는 U68 `$E082`(비트 7 = 한글, 비트 0–2 = 조합 단계), 자모 `$E086–$E089`.
* **CP/M:** SoftCard CP/M 2.20B는 HART 80컬럼 펌웨어로 U68에 출력함(확인: BIOS가 출력 `$C9AA`, 입력 `$C84D`를 6502로 부르고 글자는 `$067B`로 주고받음 — 디스크 오프셋 `$2B0C`·`$2B1F`). 80컬럼 쪽(U70)에는 한글이 없음. 콘솔을 슬롯 7 한글 드라이버로 돌리는 것은 **메모리가 겹쳐 불가능**: 드라이버가 그리는 고해상도 1·2페이지(6502 `$2000–$5FFF`)가 U5 변환표로 Z80 `$1000–$4FFF`, 곧 CP/M 프로그램 영역 한가운데라 글자를 찍을 때마다 실행 중인 프로그램이 덮임. → HART의 한글 40×24는 BASIC·DOS 쪽 기능이고 CP/M은 영문 80컬럼으로 보는 것이 맞음 (2026-11-28 판단).

## 4. 에뮬레이터에 필요한 것 (다음 단계)

> 2026-11-27: 1–4 모두 STM32 `TARGET=HART`에 들어감 (위 3.4, STM32 README "정원 HART 빌드"). 남은 것은 화면 전환(Apple/U68)의 실제 조건, `$8800`·`$0800`·`$0C00`의 뜻. 2026-11-28: 한글(PR#7)도 들어감(3.5절) — 그리는 쪽은 U64가 아니라 메인 CPU(U64는 글꼴·루틴을 U68로 넘김). U70 뱅크 0(FLASH 추정)은 아직 안 씀.

1. **U64 6502 하나 더**: U65를 `$C000`/`$E000`에, U68을 3.1 대응대로 `$4000`/`$5000`에, 키보드 행 `$8000–$800C`, 스위치 `$8800`, 래치 `$0400/$0800/$0C00`.
2. **메인 쪽**: U68을 `$E000–$E7FF`에 언제 보이게 할지(3절 의문), `$0400` 래치를 메인 `$C000` 키 입력으로 연결.
3. **화면**: U68 80×25를 U70 폰트로 그리기(행 24 = 기능키 줄). 한글: 글꼴은 U70이 아니라 U65 오프셋 `$1780` + 코드×8(`$80–$9F` 초성, `$A0–$BF` 중성, `$C0–$DF` 종성(조합형 한글 자모, 점은 비트 0이 왼쪽; 그림 [`analysis/u65_font.png`](../analysis/u65_font.png)))에 있음 → (2026-11-28 해석) U64가 직접 그리지 않음: 글꼴과 그리기 루틴을 U68로 복사해 넘기고, 메인 CPU가 고해상도 1·2페이지에 그림(3.5절).
4. **키보드**: PC 키 → HART 키 매트릭스(13행 × 8열) 표. 행·열 배치는 J10 배선([05](05-interface-pinouts.md))과 U65 스캔 루틴의 키 코드표에서 만들어야 함.
